## 会社・路線単位で拡張するための変更単位

1. 許可された取得元、路線一覧、駅の識別子と掲載ページの実リンクを会社単位のmanifestにする。推測URLを全駅分生成して巡回しない。駅名だけを識別子にしない。
2. 各manifestには出典URL、条件URLと確認日、再配布条件、改正日、取得日、検証日、適用期間、原資料SHA-256を持たせる。改正日と掲載ページの確認日を混同しない。終了日不明はnullで保持。
3. 取得は会社共通のキューで直列化し、公開側の指定頻度を優先。既存の1.1〜1.2秒間隔は独自の負荷軽減策であり許諾の証拠ではない。403/429/認証要求では停止し、プロキシや別言語を使った制限回避をしない。差分のない資料を繰り返し取得しない。
4. 同じ会社の共通変換器へmanifestを渡す。JRは日付指定を維持し、土曜・日曜・祝日を別日に検査。大阪西行の宝塚線分岐と新快速/快速/普通の表分割を保持。阪急は既存の本文言語辞書と掲載版ハッシュが未知なら未検証へ。阪神は甲子園固有の駅コード、時間帯行数、行先辞書、PDFリンクを共通処理と駅例外に分離する。
5. 出力を一時ファイルに生成し、元ファイルを上書きせず、既存版との差分を監査。便の増減、始終発、終端駅の発車不能方向、24時以降、方面/曜日の追加・欠落、改正前後、行先/種別欠落、重複を例外一覧にする。
6. 人の確認対象は、改正/条件の変更、新駅・新方面、終端、未知の凡例、全便差分、異常値に絞る。既存の検証印を新しい版へコピーしない。
7. API側、駅検索、日付キャッシュ検証、方面選択、対応一覧を同じmanifestから生成できる状態にしてから接続する。現状のJRフロント側は8方面完全一致の検査があるため、importerだけ増やすと取得結果が拒否される。`useTimetables.ts`のキー検査を無条件に緩めない。

## 非公式追加検索

`server/western-feeds.json`と`server/western-service.mjs`は既存の非公式Transit API経由の検索・参考時刻表示。会社・路線のmetadataはあるが、検索上限30件・採用8候補で全駅一覧にはならない。運行期間が未来まであっても現行ダイヤを証明しない。全方面混在、阪神の行先未収録、元資料が2026年6〜7月取得、部分取得の可能性があり、乗車判定には使わない。今回APIへの全駅巡回・再取得はしていない。

## 対応一覧・差分の再生成

`scripts/audit-kansai-coverage.mjs`はネットワークを使わず、実際の駅配列、接続済みbundle、保存JSON、過去の照合記録を読み取る。型付きソースはASTでリテラルだけ読み、アプリコードを実行しない。未知の式は停止する。

```powershell
node scripts/audit-kansai-coverage.mjs --dates 2026-10-26,2026-10-31,2026-11-01,2026-11-03 --out docs/kansai-coverage-20261026-review
npx vitest run tests/kansai-coverage.test.ts
node scripts/audit-kansai-coverage.mjs --dates 2026-10-26,2026-10-31,2026-11-01,2026-11-03 --compare docs/kansai-coverage-20261026-review.json --out docs/kansai-coverage-NEXT_TIMESTAMP
```

`--out`は拡張子なしで指定し、JSONとMarkdownを新規作成する。既存ファイルへの上書きは拒否する。再実行時は新しい時刻付き名前を使う。`--now`で監査時計を固定できるが、その場合は実際の当日確認と呼ばない。監査時刻は検証日を書き換えない。

出力は駅×路線×方面×指定運行日のセルを持つ。「検索」「取得」「既存検証印」「照合記録」「当日有効」「乗車目安の時刻表条件」を分け、出典・利用条件は本資料と元表注記に保持する。当日有効は静的な保存データからの判定で、実行中API、端末のキャッシュ、利用者の徒歩経路は監査しない。JRの当日取得可能性は当日有効件数に含めない。足りない時刻表を別日・別駅のデータで補完しない。

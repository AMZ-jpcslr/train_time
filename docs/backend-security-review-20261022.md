# バックエンドのコードレビューと修正

確認日: 2026-10-22（Asia/Tokyo）。ユーザー指定の `backend-security-coder` スキルを読み、公開・アカウント不要の小規模試作を前提にレビューしました。秘密情報を含む `.env` は閲覧していません。

対象は `server/api.mjs`、`server/walking-service.mjs`、`server/cloud-routing.mjs`、`server/cloud-jr.mjs`、`server/cloud-services.mjs`、`server/redis.mjs`、`server/jr-service.mjs`、`api/index.mjs`、`scripts/import-jr.mjs`、経路を受け取るフロントの検証処理、既存のバックエンドテストです。

## 指摘と対応

### P2: 異なる徒歩要求が無制限に待機する — 修正済み

修正前の `server/walking-service.mjs` の `route()` は、異なる座標をすべて Promise キューと `inflight` に追加していました。回数制限は順番が到来した後の処理にあり、上流応答が遅い間に要求数・座標・HTTP処理を無制限に保持できました。

外部の `fetch` を未解決の Promise に差し替えたローカル再現では、異なる座標1,000要求に対して、上流呼び出し1件、早期拒否0件、待機1,000件でした。実在サービスへの負荷試験はしていません。

修正後は、実行中を含む異なる要求をプロセスごとに8件までとし、それ以上を即時拒否します。同一要求は従来どおり集約します。処理完了・失敗の両方で枠を解放し、直列化用 Promise には完了した経路結果を残しません。外部サービスの共有ロック・回数制限はそのままです。

### P2: 経路応答・形状・キャッシュのサイズに実用的な上限がない — 修正済み

修正前は `response.json()` で全応答を読み込み、フル形状を最大120件キャッシュしていました。取得のタイムアウトはありましたが、応答サイズの上限はなく、異常に大きな形状はFunctionのメモリーやフロントの頂点処理を圧迫できました。

修正後の制限は以下のとおりです。

| 対象 | 制限・処理 |
|---|---|
| 応答本文 | 2MiB。ネイティブfetchの本文ストリームを数え、超過時点で読み取りをキャンセル |
| Content-Length | 大きすぎる値は事前拒否。欠損・偽の小さい値でも実バイト数の制限を適用 |
| 経路の形状 | 最大20,000頂点。各頂点は有限な経度・緯度2要素 |
| 経路案内 | 最大2,000件。徒歩モード、非負の有限距離、文字列型・長さを検証 |
| 案内の道路名 | 最大512文字。オブジェクト等を画面に渡さない |
| メモリーキャッシュ | JSON換算で合計8MiB、最大120件、10分の有効期限 |
| 期限切れの座標 | タイマーと要求時の掃除で破棄。将来時刻の記録も再利用しない |
| HTTP 429 / 5xx | 未読の本文をキャンセルして既存バックオフを適用 |

テスト用などの独自fetchアダプターがストリームを持たず、解析済みJSONだけを返す場合も、利用・キャッシュ前にJSONのバイト数を制限します。実際のNode fetchでは、本文を全量読み終える前のストリーム制限が働きます。

8MiBはキャッシュ内容のJSON換算値です。JavaScriptオブジェクトや処理中バッファを含むプロセス全体のヒープ使用量が8MiB以内という意味ではありません。サーバーレスのプロセスが凍結されている間のタイマー実行や物理メモリー消去時刻も保証しません。再開後の要求時には期限切れを再利用せず掃除します。

## 検証

```powershell
npm test -- tests/walking-security.test.ts tests/walking.test.ts tests/cloud-backend.test.ts
```

結果: **3ファイル・48件すべて成功**。このうち `tests/walking-security.test.ts` に追加した回帰テストは16件です。

- 応答が止まった状態の1,000要求で、8件だけを待機させ、残り992件を早期拒否する。
- 上限到達中も同じ要求を集約し、完了後は次の要求を受け付ける。
- サイズ超過をヘッダー・実ストリーム両方で検出し、読み取りキャンセルと共有リース解放を確認する。
- Content-Length欠損・過小申告・UTF-8を含む上限ちょうどの本文を検証する。
- 巨大形状・過剰な案内・不正な文字列型・無限大の距離を拒否する。
- 新たな要求がなくても動作中のタイマーが期限切れを削除し、時計の前後変動でも期限切れ・将来の記録を再利用しない。
- キャッシュの件数が120未満でも、合計サイズに応じて古い記録を追い出す。
- 既存の200m道路探索、道路までの接続区間と乗車判定の区別、プロバイダーエラー分類、共有回数制限との互換を確認する。

これらはすべて合成座標・注入したResponse/ReadableStream・Redisの契約テスト用ダブルを用いたローカル検証です。現在地を取得せず、実際のFOSSGIS・JR・Redisへの通信や攻撃試験を行っていません。

## そのほか確認したことと境界

- APIは決められたパス・HTTPメソッド・JSONサイズ・同一サイト要求を検査する。
- 利用者が送るのは座標と既存の駅/入口IDであり、任意の外部取得URLを指定できない。
- JRリンクは公式オリジンと数値IDから構築し、HTML中のJavaScriptを実行しない。
- Redisトークンをクライアント設定や公開エラーに含めず、GPS座標をRedisへ保存しない。
- 公開APIの共有制限はRedis障害時に外部取得を停止し、プロセス内制限だけへ切り替えない。
- 既存のAPI入力検査・Redis共有制限・失敗時のエラー抑制は、今回の対象テストでも成功した。

レビュー範囲ではP1以上の具体的な問題は確認されていません。ただし網羅的な侵入試験やVercel基盤の監査ではありません。実Redis上のLua、実環境の通信・ログ設定の確認は別です。ログイン不要の試作であり、上限は全利用者で共有します。大量アクセス下の可用性や利用者ごとの公平性を保証するものではありません。

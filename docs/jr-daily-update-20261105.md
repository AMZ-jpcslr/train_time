# JR当日取得の表記差修正（2026-11-05）

## 原因と変更

対象リポジトリは `AMZ-jpcslr/train_time`、調査時のmainは `f412a1f`。
公開サイトの `/api/config` は `jrEnabled: true` / `sharedControls: configured` だったが、`/api/jr?date=2026-11-05` は `status: unavailable`、空の表と15分後の再試行時刻を返した。共有キャッシュの未設定ではなかった。

同じ日の公式ページを既存パーサーで読むと `Displayed operating date mismatch` を再現した。日付選択欄の `2026年11月05日(木)` と見出しの `2026年11月5日(木)` を文字列の完全一致で比較していたため。初回検証の10月22〜25日は月日がともに2桁で、この不具合を検出できなかった。1〜9日、1〜9月にも影響する。

`scripts/import-jr.mjs` で、両方の表示が要求された年月日に一致することを確認した上で、月日のゼロ埋めを正規化して比較する。曜日の一致、日付選択値、駅・路線・方面、PC/モバイル全便整合、取得時刻と6時間の鮮度制限は維持した。別日の表や過去の曜日パターンへの置換は行わない。画面の取得不能表示と再試行処理は既存のまま。

月だけ・日だけ・両方がゼロ埋めされたケース、および表示日の不一致、曜日違い、見出し欠損を回帰試験に追加した。

## 実データ検証

修正後、2026-11-05運行日の既存4駅8方面を通常HTTPS GETで1回取得し、`collectJr` とサーバーの `validateResult` を通過した。計1,702便。西宮216/217便、大阪東295/西238便、茨木219/224便、南草津144/149便。大阪西の宝塚線分岐除外も既存どおり。元HTMLのSHA256と実取得日時・件数は [検証要約](jr-daily-update-20261105.json) に保存した。

診断原本・正規化表はGit対象外の `.cache/jr-diagnostic-sources/.cache/jr-public/2026-11-05/` と `.cache/jr-diagnostic-result.json` のみに保存し、配信用の `src/data/jr.json` は変更していない。公開APIの実行環境では修正コードを未検証。

全519件の単体テストと `npm run build` が、Node.js 22.18.0の既定環境と本番指定のNode.js 24の両方で成功。最初のサンドボックス内テストは一時ファイルrenameのEPERMにより9件失敗したため、通常権限で全件を再実行し成功を確認した。詳細ログは `.cache/test-results-20261105.json`、Node.js 24版は `.cache/test-results-node24-20261105.json`。ビルドには既存の大きなフロントエンドchunkについて警告があるが、失敗はない。

## 自動更新と公開反映

新しいスケジューラーや鍵は不要。既存の利用時オンデマンド更新を使う。JST04:00で運行日を切り替え、日別に4駅8方面を取得し、Redisで6時間共有する。同時取得は分散ロックで抑制、元サイトへの取得間隔は1.2秒、失敗後15分は再取得を抑制する。ブラウザーも実取得期限と再試行時刻に従って自動更新する。常駐・定時の先読みは追加していない。

この修正を公開へ反映するには、修正内容の承認後にGitHubへpushして既存Vercel連携でデプロイする必要がある。失敗記録が残っていれば `retryAfter` の後に再試行する。公開APIが `status: ready`、指定運行日、8表、実取得日時、6時間以内の失効日時を返し、画面で表示できるかを確認する。Redis削除・環境変数変更は不要。今回push、デプロイ、外部設定変更、秘密情報の作成は行っていない。
